# PRODUCT.md — GenUI 受控原型产品文档

本文档定义产品边界：解决什么问题、为谁服务、MVP 做什么、明确不做什么、用什么指标衡量成功。架构边界见 [ARCHITECTURE.md](ARCHITECTURE.md)，术语见 [GLOSSARY.md](GLOSSARY.md)。

## 1. 问题陈述 (Problem Statement)

小白用户不会写代码，也不会描述精确坐标。在"用 AI 生成网页"的真实场景里，他们最自然的表达方式是：**在页面上指着某个东西说"把这个改一下"**。

现有方案的两个失效点：

1. **整页重生成不可控**：每一轮对话都把整页重新生成一遍，用户之前改好的部分会被冲掉，状态漂移，信任崩塌。
2. **指代无法传递**：用户选中了"那个按钮"，但模型不知道"那个"是哪个——没有稳定的控件身份与传递协议。

本产品是一个受控的 GenUI 原型，用受控 JSON DSL + 结构化局部 Patch 证明：可以只改选中控件、其余部分零漂移，并且通过模板复用让新用户用更少的对话轮次拿到可用页面。

## 2. 目标用户 (Target User)

- **主要角色**：不会写代码的小白用户（店主、运营、学生等），想要一个简单可用的网页（落地页 / 表单 / 卡片列表）。
- **次要角色**：面试评估者——通过演示与文档考察系统设计、Prompt 工程与机制设计能力。

## 3. 核心用户旅程 (Primary User Journey)

1. 用户用一句话描述需求（例如"帮我做一个咖啡店落地页"）。
2. 系统生成（或从历史模板匹配）一个 DSL 页面初稿并渲染。
3. 用户在页面上点击选中一个具体控件（如主按钮），控件出现清晰的选中态。
4. 用户用自然语言下达精修指令（"文案改成『立即预约』""颜色换成深棕色""尺寸大一点"）。
5. 系统只修改选中控件，页面其余部分保持不变；用户可连续多轮精修。
6. 用户确认页面可用，流程结束；系统记录本轮对话的轮次与编辑轨迹。
7. 后续相似需求的新用户，直接获得历史模板推荐作为起点，用更少轮次完成。

## 4. MVP 功能 (MVP Features)

| # | 功能 | 说明 |
|---|------|------|
| F1 | 一句话生成初稿 | 单页前端，输入一句话产出 DSL 页面（落地页 / 表单 / 卡片列表其一即可演示） |
| F2 | 控件选中 | 点击或框选选中一个控件，有清晰的选中态视觉反馈 |
| F3 | 局部精修 | 自然语言指令 → 后端返回结构化 Patch → 只更新选中控件，其余零变更 |
| F4 | 多轮上下文 | 连续多轮精修，保留对话与页面状态上下文，状态不漂移 |
| F5 | 确定性校验 | 模型输出经 Schema 校验 + 业务规则校验 + Patch 边界校验后才应用 |
| F6 | 模板推荐 | 从（模拟）历史对话沉淀模板，新对话按初始意图匹配推荐 |
| F7 | 指标展示 | 页面展示完成任务所需对话轮次等核心指标 |

## 5. 支持的组件 (Supported Components)

第一版固定组件集（未注册类型一律拒绝）：

`Page` · `Section` · `Heading` · `Text` · `Button` · `Image` · `Card` · `Form` · `Input`

每个组件的可编辑属性集合由 DSL Schema 定义；Patch 只能触及 Schema 允许的属性。

## 6. 局部精修工作流 (Local Editing Workflow)

1. 用户选中节点 → 前端记录 `selectedNodeId`（编辑上下文，不属于 DSL 节点内容）。
2. 用户输入指令 → 前端把 `{ 指令, 选中控件上下文, 当前页面状态 }` 发给后端。
3. 后端经 Model Provider 获得**候选输出**（Candidate Output）。
4. 候选输出依次通过：Schema 校验 → 业务规则校验 → Patch 边界校验。
5. Patch 先应用到文档**副本**，对非目标子树做完整性校验（零变更）。
6. 全部通过才提交为新页面状态，并记录 Trace；任一步失败则拒绝并给出可理解的反馈。

## 7. 模板推荐概念 (Template Recommendation Concept)

- **沉淀**：从历史对话 / 生成结果中提取可复用模板（意图特征 + 页面结构）。
- **推荐**：新对话的初始意图与模板库匹配，命中即以模板为起点，跳过从空白开始的若干轮。
- **自进化**：随新数据对模板库做新增 / 合并 / 淘汰，形成闭环（触发条件与更新策略在架构文档与后续 Spec 中定义）。
- 实现只用规则 / 简单聚类 / embedding 检索，不引入复杂模型。

## 8. 成功指标 (Success Metrics)

**北极星指标**：达到"用户确认页面可用"状态所需的**中位对话轮次**。

辅助指标：

| 指标 | 采集方式 |
|------|----------|
| 首稿接受率 | 首稿后用户未要求结构性重做即进入精修的比例 |
| 局部修改成功率 | Patch 通过全部校验并成功应用的比例 |
| 非目标区域零变更率 | 应用 Patch 后非目标子树哈希不变的比例（目标为 100%） |
| 模板推荐采用率 | 推荐模板被采纳为起点的比例 |
| 完成任务总时间 | 从进入对话到确认可用的墙钟时间 |
| 定稿前编辑量 | 确认可用前的 Patch 应用次数 |
| 模型输出校验失败率 | 候选输出被任一校验环节拒绝的比例 |

## 9. MVP 演示场景 (MVP Demo Scenario)

1. 用户输入咖啡店落地页需求；
2. 系统生成或加载 DSL 页面；
3. 用户点击选中主按钮；
4. 用户连续修改按钮文案、颜色和尺寸；
5. 系统证明非目标节点没有变化（零变更校验结果可见）；
6. 相似的新需求可以获得历史模板推荐；
7. 页面展示完成任务所需对话轮次等指标。

## 10. 明确的非目标 (Explicit Non-goals)

- 任意网页和任意组件生成；
- 模型直接生成并执行代码；
- 拖拽式编辑器；
- 多用户权限；
- 计费系统；
- 多 Agent；
- 向量数据库；
- Figma、飞书、Jira 等第三方集成；
- 通用生产级低代码平台；
- 第一版自动训练模型。

## 11. 产品风险 (Product Risks)

| 风险 | 影响 | 缓解 |
|------|------|------|
| 模型输出不稳定，频繁校验失败 | 精修成功率低、体验差 | 三层收敛：生成时结构化约束 + 无损规范化 + 至多一次精准 repair；失败反馈分层可读（含请求编号），绝不向用户暴露内部校验原文 |
| 固定组件集表达力不足 | 演示页面简单 | 主动收窄演示场景（咖啡店落地页），非目标已声明 |
| 模拟历史数据与真实分布偏差 | 模板机制说服力弱 | 明确记录数据假设；用 Gold Case 做确定性验证 |
| 局部修改边界蔓延（用户想改整区） | 超出 Patch 约束 | 产品上将"整页重构"与"局部精修"区分为两种意图，MVP 只承诺后者 |
| 指标不可采集 | 无法证明机制有效 | 每个指标在架构中有明确埋点（Trace） |

## 12. MVP 完成定义 (Definition of MVP Complete)

同时满足以下条件，MVP 视为完成：

1. 演示场景（第 9 节）七步全部可现场跑通；
2. 多轮精修中非目标区域零变更率 = 100%（有自动化校验证据）；
3. 模板推荐在模拟数据上形成"沉淀 → 推荐 → 更新"闭环，并可演示；
4. 北极星指标与辅助指标可被采集并在页面展示；
5. 关键协议（DSL / Patch / Provider 边界 / 模板机制）有正向 + 反向测试；
6. 设计文档（产品、架构、术语、ADR）与实现一致，无遗留矛盾。
