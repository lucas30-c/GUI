# Specs — 任务规格说明

本目录存放驱动开发的任务 Spec。**没有 Spec 就不动手**——每份 Spec 对应一个小型、可独立验收的任务，Agent 只能执行当前 Spec 允许的范围。

## 命名方式

```text
NNN-short-title.md
```

三位递增序号 + 英文小写短横线标题，例如 `001-dsl-schema.md`。序号不跳号、不复用。

## 每份 Spec 必须包含的小节

| 小节 | 内容 |
|------|------|
| **目标 (Goal)** | 这份 Spec 要达成什么，一句话说清 |
| **背景 (Context)** | 为什么现在做、依赖哪些已完成的前置 Spec、相关文档链接 |
| **范围内 (In Scope)** | 本任务要做的事，逐条列清 |
| **范围外 (Out of Scope)** | 明确不做的事（防止范围蔓延） |
| **允许的文件 (Allowed Files)** | 本任务允许新建/修改的文件清单（可含目录通配） |
| **禁止的变更 (Forbidden Changes)** | 本任务明确禁止的变更（协议、依赖、测试等） |
| **功能需求 (Functional Requirements)** | 编号的功能要求，可逐条对应验收 |
| **验收标准 (Acceptance Criteria)** | 编号的、可客观判定的 PASS/FAIL 标准 |
| **验证命令 (Verification Commands)** | 验收时实际运行的命令；若当前阶段没有可运行命令，必须写明原因 |
| **审批闸门 (Approval Gates)** | 本任务触碰到的 AGENTS.md §6 闸门（没有则写"无"） |
| **完成报告 (Completion Report)** | 指向 AGENTS.md §10 的报告格式 |

## 规则

1. 每份 Spec 对应一个小型、可独立验收的任务；宁可拆小，不可堆大。
2. Agent 不得自行扩大范围；发现 Spec 缺失、矛盾或需要架构决策时，必须暂停并报告（AGENTS.md 约束 14）。
3. 当前 Spec 完成并通过验收后，才进入下一份。
4. Spec 的验收标准不得在实现过程中被擅自修改；确需修改时走审批闸门，并记录修改理由。
5. 如果暂时没有可运行的验证命令，应在 Spec 中明确说明原因，**不能伪造验证结果**。
6. Spec 可以让规则更严格，但永远不能放宽 AGENTS.md；冲突时以更严格的安全和范围约束为准。
